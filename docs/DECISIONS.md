## ADR-001 Tech stack
**Decision.** Keep the brief's defaults: Python 3.12 + uv (lockfile committed), FastAPI, SQLAlchemy 2 + Alembic, SQLite WAL, Pydantic v2, asyncssh, httpx, APScheduler, Jinja2 + HTMX + Cytoscape.js (vendored, no Node), official MCP SDK, pytest + hypothesis, ruff, mypy, Typer for the CLI, structlog for logging. Task runner: **poethepoet** tasks in `pyproject.toml` as the single source (`uv run poe check` works on Windows and Linux). The Makefile is a thin wrapper for Linux/CI.
**Rejected.** Make as the primary runner (not on stock Windows); `just` (extra binary); Node/Vite for the UI (build step, supply chain); Go (single binary, but the MCP SDK and team skills favour Python).
**Consequences.** CI matrix ubuntu + windows on 3.12 (3.13 added as non-blocking).

## ADR-002 Target-side SSH enforcement: forced-command probe (option a)
**Context.** SSH exec has no argv on the wire. The client sends one string that sshd hands to the user's login shell (`$SHELL -c "<string>"`). Client-side argv discipline therefore can't be the only control. Docker-group membership is root-equivalent and excluded.
**Decision.** Option (a), implemented in two scripts generated by `atlas targets render` into `docs/targets/` for the owner to install:
1. `authorized_keys` for the dedicated user `atlas-ro` (no password, shell `/bin/bash`, home not writable by others):
   `restrict,from="<collector-ip>",command="/usr/local/libexec/atlas-probe-gate" ssh-ed25519 AAAA… atlas@collector`
   (`restrict` disables pty, agent, port and X11 forwarding, and user rc.)
2. `atlas-probe-gate` (root-owned 0755, runs as `atlas-ro`): exact-matches `$SSH_ORIGINAL_COMMAND` against a fixed list (`atlas-probe os|net|ports|storage|services|cron|users|packages|docker|pi|version`). No splitting, globbing or eval. On a match it execs `sudo -n /usr/local/libexec/atlas-probe <section>`. Anything else exits 64 and is logged to syslog.
3. `/etc/sudoers.d/atlas-ro`: one exact-argv line per section (`atlas-ro ALL=(root) NOPASSWD: /usr/local/libexec/atlas-probe os, … `). No wildcards. `Defaults:atlas-ro !requiretty, env_reset, secure_path=…`.
4. `atlas-probe` (root-owned 0755, bash, Debian/Ubuntu): runs only read-only commands with fixed arguments and takes no free-form parameters. The docker section uses `docker inspect --format` with an **allowlisted field template**: `.Config.Env` is reduced to names *on the target*, and `Cmd`/`Args`/`Labels`/`Healthcheck` are emitted for collector-side redaction. Output is framed with a per-run random boundary so data can't forge section headers. The `version` section reports the probe SemVer and its own SHA-256; `atlas doctor` compares that to the expected hash.

**Rejected.**
- (b) sudoers listing docker/ss/etc. commands directly: sudoers argument matching is glob-based and easy to get wrong (`docker inspect *` allows `--format` template injection and `docker inspect` of arbitrary objects). The command surface becomes N binaries × their flags, and the client string still reaches a shell.
- (c) docker-socket-proxy (e.g. tecnativa) on a private interface: it adds a network listener on every host, and `GET /containers/{id}/json` still returns Env values, so secrets would cross the wire. It only covers Docker, so linux-ssh would still need (a) or (b).
- docker group: root-equivalent.
- An agent daemon: excluded by non-goals.

**Consequences.** The probe is a reviewed artefact with a version. Changing collector requirements regenerates it, and the owner reinstalls. Without sudo, sections that need root (ports with process owners, docker, root crontabs) degrade to partial results.

## ADR-003 Client-side SSH runner
**Decision.** `SshRunner` accepts only `ProbeSection` enum members (no strings). The exec string comes from a constant table, so there is no interpolation. Options: asyncssh `client_keys=[per-target ed25519]`, `known_hosts=<pinned file>` (unknown or changed key ⇒ refuse), `agent_path=None`, `agent_forwarding=False`, `x11_forwarding=False`, `request_pty=False`, `preferred_auth="publickey"`, `password=None`, connect/command timeouts, max output bytes (default 8 MiB) and line-length caps. No `subprocess`, no `shell=True` anywhere. A ruff `banned-api` rule and a test grep for it. A `demo:` transport replays fixtures behind the same allowlist.
**Rejected.** Paramiko (sync, weaker typing); OpenSSH binary via subprocess (Windows path and quoting issues).
**Verified (M1, asyncssh 2.24.1).** Option names were checked against the installed `SSHClientConnectionOptions`. `config=None` loads no `~/.ssh/config`. `agent_path=None` resolves to no agent; the default `()` would fall back to `SSH_AUTH_SOCK`. `known_hosts=(pins, [], [])` trusts exactly the pinned keys with no hostname matching, no CAs and no TOFU. Host key algorithms are limited to ed25519/ECDSA-P256, client keys to ed25519. Tests drive an in-process asyncssh server, including a hostile `~/.ssh/config`, a conflicting `known_hosts` and a bogus `SSH_AUTH_SOCK`.

## ADR-004 Proxmox access
**Facts.** PVE 9.2 is current (released 2026-05-21, Roadmap). PVE 9 dropped `VM.Monitor` and added `VM.GuestAgent.{Audit,FileRead,FileWrite,FileSystemMgmt,Unrestricted}`. `VM.GuestAgent.Audit` was added to the `audit` privilege group with `VM.Audit` (pve-devel series 2025-07-17, access-control patch 1/9), and PVEAuditor is, as far as I can tell, built from the audit groups in `AccessControl.pm` (not confirmed by a primary doc; verify at M3 with `pveum role list`). Separated API tokens get the intersection of user and token ACLs (User Management wiki). Backup job API: `schedule` replaces `starttime`/`dow` (9.2 notes).
**Decision.** User `atlas@pve` (no password login needed), token `atlas@pve!collector` with **privsep=1**, role **PVEAuditor** on `/` for both the user and the token. If the guest-agent IPs come back empty, add a custom role `AtlasGuestAudit = VM.GuestAgent.Audit`. `atlas doctor` reads `GET /access/permissions` and **fails if any non-Audit privilege is present**. TLS: pin the PVE CA or leaf fingerprint. Endpoints (GET): `/version`, `/cluster/status`, `/cluster/resources`, `/cluster/backup`, `/cluster/backup-info/not-backed-up`, `/cluster/ha/resources`, `/cluster/sdn/vnets`, `/nodes`, `/nodes/{n}/status`, `/nodes/{n}/network`, `/nodes/{n}/storage`, `/nodes/{n}/qemu`, `/nodes/{n}/qemu/{id}/config`, `/nodes/{n}/qemu/{id}/agent/{network-get-interfaces,get-osinfo}`, `/nodes/{n}/lxc`, `/nodes/{n}/lxc/{id}/config`, `/nodes/{n}/lxc/{id}/interfaces`. **Verified at M3 (2026-10-18) against the PVE source**, which is what the API viewer is generated from. The complete allowlist and the privilege each endpoint checks are in `collectors/proxmox/endpoints.py`:
- `/cluster/status`, `/cluster/backup` and `/cluster/backup-info/not-backed-up` check `Sys.Audit` on `/`.
- `/cluster/resources` filters per object by `VM.Audit`, `Sys.Audit`, `Datastore.Audit` and `SDN.Audit`.
- qemu/lxc `config` and lxc `interfaces` check `VM.Audit`.
- `agent/network-get-interfaces` and `agent/get-osinfo` are **GET** endpoints and need `VM.GuestAgent.Audit` (or `.Unrestricted`). `exec`, `file-read`, `file-write` and `set-user-password` need `.FileRead`, `.FileWrite` or `.Unrestricted`, which PVEAuditor does not have; they also sit on the denied-segment list.
- `/nodes/{n}/network` is open to any user, but bridges are hidden without SDN access (PVEAuditor has `SDN.Audit`).
- `/access/permissions` lets a token dump its own permissions.

PVEAuditor is confirmed to be the union of every category's `audit` group, and that includes `VM.GuestAgent.Audit` (AccessControl.pm `create_roles`). `atlas doctor` fails if the token holds any privilege outside the `*.Audit` set.
**Rejected.** root@pam token (full write); a PVEVMUser-type role (VM.PowerMgmt); SSH + `pvesh` on the nodes (shell on a hypervisor).
**Sources.** git.proxmox.com (HEAD, 2026-10-18): qemu-server `src/PVE/API2/Qemu/Agent.pm`; pve-container `src/PVE/API2/LXC.pm`; pve-manager `PVE/API2/{Cluster,Backup,Network}.pm` and `PVE/API2/Cluster/BackupInfo.pm`; pve-access-control `src/PVE/AccessControl.pm` and `src/PVE/API2/AccessControl.pm` · https://pve.proxmox.com/wiki/User_Management · https://pve.proxmox.com/wiki/Roadmap · https://lists.proxmox.com/pipermail/pve-devel/2025-July/073214.html · https://lore.proxmox.com/pve-devel/20250717133711.84715-9-f.ebner@proxmox.com/

## ADR-005 UniFi access
**Facts.** The official local **Network Integration API** is served at `https://<console>/proxy/network/integration/v1/...`, needs Network ≥ 9.3, and authenticates with header `X-API-KEY`. The newest reference seen is v10.6.102. Lists are paginated with `offset`/`limit` (max 200) plus `filter`. Read coverage (v10.3.58 reference): info, sites, devices + details (ports, radios, `uplink.deviceId`) + latest stats, clients, networks, Wi-Fi broadcasts, firewall zones/policies/ordering, ACL rules, DNS policies, traffic matching lists, switch stacks/LAGs/MC-LAG, WANs, VPN, RADIUS profiles, device tags. The same API exposes POST/PUT/PATCH/DELETE and **actions** (device/port/client actions, vouchers). **API keys have no read-only scope; a key inherits the permissions of the admin who created it.** The Integration API reportedly does **not** expose uplink port numbers, client→switch port mapping or LLDP; those live only in the Classic API (`/proxy/network/api/s/{site}/stat/device`, `/stat/sta`), which uses session login `POST /api/auth/login` and `X-CSRF-Token`.
**Decision.**
1. Primary: the Integration API with a key created **while logged in as a dedicated local admin limited to Network "View Only"** (restricted to local access, no MFA prompt path). If UniFi OS won't let a view-only admin mint keys, SECURITY.md will say so explicitly. The control is then the GET-only wrapper plus the key living only in a Docker secret, and the risk is documented.
2. Wrapper: GET only on an endpoint-template allowlist. **No** POST is registered for the Integration API. All `/actions` paths are blocked by an explicit deny pattern on top of the allowlist.
3. Wi-Fi: PSK/passphrase fields are dropped by the response schema (never parsed). The Redactor also covers `x_passphrase`, `passphrase`, `psk`, `wpa*key`.
4. Classic enrichment is **opt-in** (`legacy_enrichment: true`). It uses a separate view-only local account. The only registered POSTs are `/api/auth/login` and `/api/auth/logout` (schema-checked bodies, the password supplied by SecretResolver at send time and never logged). Reads are GET `stat/device`, `stat/sta`, `rest/portconf`, `rest/networkconf`.
5. `atlas doctor` reads `GET /v1/info` and records the app version. It warns if the version is newer than the tested schema set.

**Rejected.** The cloud Site Manager / connector API (`api.ui.com`, cloud dependency); SSH to the UCG (shell on the gateway, vendor discourages it); SNMP (UCG coverage is thin and gives no clients or firewall data); `aiounifi` / `unifi-controller-api` libraries (they bring write paths, and wrapping our own client keeps the read-only guarantee in our code).
**Sources.** https://developer.ui.com/network/v10.6.102/updatefirewallzone (version index) · https://developer.ui.com/network/v9.3.43/getdevicedetails · https://github.com/gigabrit/unifi-network-api-reference (v10.3.58, community) · https://github.com/uchkunr/unifi-best-practices (v10.1.68, community: key inherits creator permissions, Classic login/CSRF). **Verified at M4 (2026-10-18)** against the official OpenAPI spec, Network **v10.6.106** (https://developer.ui.com/network/v10.6.106/openapi.json; version index at https://developer.ui.com/llms.txt):
- **Server and auth:** server `https://{consoleIP}/proxy/network/integration`, header `X-API-KEY`.
- **Pagination:** lists are paginated with `offset`/`limit` (max 200), and responses come as `{offset, limit, count, totalCount, data}`.
- **Fields used:**
  - device `state` enum: ONLINE, OFFLINE, …, CONNECTION_INTERRUPTED;
  - device details: `interfaces.ports` / `radios`, `uplink.deviceId`;
  - clients: wired and wireless, both with `macAddress` and `uplinkDeviceId`;
  - networks: `vlanId`, `management`, `ipv4Configuration.hostIpAddress` / `prefixLength`;
  - firewall zones (`networkIds`) and policies (`action.type`, `source/destination.zoneId`, `index`, `loggingEnabled`).
- **Passphrases:** Wi-Fi security schemas carry `passphrase` inside `securityConfiguration`. The collector reads only `securityConfiguration.type`, and the per-SSID details endpoint is **not registered at all**. `hotspot/vouchers` and `statistics` aren't registered either.
- **Allowlist:** in `collectors/unifi/endpoints.py`, GET only.
- **Not verified:** the port-object fields (`idx`, `connector`, `maxSpeedMbps`, `speedMbps`, `poe.enabled`) come from the v9.3.43 docs sample, because that schema wasn't in the parts of the v10.6.106 spec I could read. Port state and speed are volatile anyway.
- **Classic-API enrichment** (uplink port numbers, LLDP) is **not implemented** in M4. Integration-API `uplink.deviceId` is enough for the gateway → switch → AP tree. It will be added only if per-port topology turns out to be needed.
- `atlas doctor` checks the Network version (≥ 9.3) and says plainly that key scope cannot be verified.

## ADR-006 UNAS (UniFi Drive)
**Facts.** No official public UNAS/Drive API was found. Community integrations read `https://<unas>/proxy/drive/api/...`. With an API key you get storage, pools, disks, SMART and system data. Shares and snapshots need a local account (tested on UniFi OS 5.1.19 / Drive 4.3.6; 401 regressions seen on 5.1.33). Ubiquiti advises against SSH unless support asks, and the UNAS Pro runs its own sshd.
**Decision.** Best effort, in this order: (1) UniFi Network device record if the UNAS appears there; (2) Drive GET API behind `nas.drive_api: true` (API key only, GET allowlist, schema-tolerant parsing, every field optional); (3) `manual/nas.yaml` fallback merged as a "manual" facet. No SSH.
**Rejected.** SSH probe (appliance, vendor guidance); SMB/NFS enumeration (wrong layer, needs credentials).
**Implemented at M4.**
- `drive_api: true` uses three GET endpoints a Drive API key can read (`/api/system`, `/proxy/drive/api/v2/storage`, `/proxy/drive/api/v2/systems/device-info`), as described in the community docs (`docs/API.md`, UniFi OS 5.1.19 / Drive 4.3.6). Every field is optional.
- Otherwise the owner writes `<config>/manual/<name>.yaml`, which accepts only the keys model, mac, firmware, pools, disks and shares.
- The UNAS shows up in UniFi as a client and is matched to the NAS entity by MAC.
**Sources.** https://github.com/LayerTM/unifi-unas-ha · https://help.ui.com/hc/en-us/articles/204909374-Connecting-to-UniFi-with-Debug-Tools-SSH. Verify at M4.

## ADR-007 Docker data path
**Facts.** Docker Engine API is at 1.56 (Engine 29.8). Engines from 29.3 on support API ≥ 1.40 (docs.docker.com/reference/api/engine).
**Decision.** Use the docker **CLI inside the probe** (`docker ps -a -q --no-trunc`, `docker inspect --format '<allowlisted template>'`, `docker image ls --format json`, `docker network inspect`, `docker volume ls --format json`, `docker compose ls --all --format json`). Compose project/service come from the `com.docker.compose.*` labels. Compose files are never read.
**Template (M3).** The probe runs `docker inspect --format` with an allowlisted template (templates/atlas-probe.sh):
- `.Config.Env` is reduced on the target to names via `index (split . "=") 0`.
- Maps and lists end with a `null` / `"_"` sentinel, so the template never emits dangling commas. The parser drops the sentinels.
- Container, image and network IDs come from `docker … -q --no-trunc` and are re-validated as 64-hex before being passed back as arguments after `--`.
- `docker compose ls --all --format json` gives `Name`, `Status` and `ConfigFiles`.

`split`, `json` and `index` are documented docker/Go-template functions (docs.docker.com/engine/cli/formatting). **Not yet run against a real engine;** verify at the first live scan (`atlas doctor` + one scan).
**Rejected.** The remote Engine API over TCP/TLS (write-capable, and the socket is root); socket-proxy (ADR-002c).
**Sources.** https://docs.docker.com/reference/api/engine/

## ADR-008 Read-only HTTP client
**Decision.** `ReadOnlyHttpClient` wraps httpx and accepts only `Endpoint` objects from a registry (`method`, `path_template`, typed path vars with regexes, allowed query keys, optional body schema for registered POSTs). Rules:
- Methods: GET, plus registered POSTs only.
- No `X-HTTP-Method-Override` family headers.
- Base URL pinned per source; redirects disabled.
- Path vars are validated, then percent-encoded. The final URL is re-parsed and must canonically equal the template expansion (catches `..`, `%2e`, `%252e`, `;`, `//`, backslash, NUL, unicode dot variants).
- TLS verify always on, with CA/fingerprint pinning. Response size and time caps.
- Every call goes through AuditLog with the template, never the expanded query values.

hypothesis-based fuzz tests try bypasses.
**Rejected.** Method allowlisting alone (path tricks reach action endpoints); per-collector raw httpx (no single choke point).

## ADR-009 Redaction
**Decision.** Two layers:
- **At source**: the probe's docker template emits env names only. Schemas never parse PSK, password or token fields.
- **Collector side**: `Redactor` runs over every model before persistence or logging, and as the final structlog processor. It uses:
  - key-name rules (`*pass*`, `*secret*`, `*token*`, `*key*` except an allowlist like `ssh_host_key_fingerprint`, `psk`, `auth`, `credential`, `dsn`);
  - value rules (PEM blocks, JWTs, `ghp_/gho_/github_pat_`, `glpat-`, AWS `AKIA…`/secret pattern, Slack, Stripe-like `sk_live_`, bearer headers, URL userinfo `scheme://u:p@`, DB DSNs);
  - CLI flags (`--password=x`, `-p x` in known tools, `--token x`, `PASSWORD=x cmd`);
  - cron/healthcheck lines;
  - a Shannon-entropy fallback for long tokens in argv/labels.

**String lists are treated as possible argv** (container `cmd`, `healthcheck`):
- A flag whose name is secret (`--http-api-token`, `--api-key`, but not `--password-file`) redacts the next element.
- Tool-specific short flags (`sshpass -p`, `redis-cli -a`) are handled.
- Contextual rules see the whole command line.

Both cases were found by the M3 leak test, not by inspection.
Replacement is `«redacted:<rule>:<sha256[:8]>»`. The hash is HMAC-keyed with a local secret, so change detection still works without dictionary attacks. Redaction counts are recorded per run.
**Rejected.** Only key-name rules (misses cmdline secrets); a full gitleaks ruleset at runtime (heavy). The gitleaks patterns are reused as a test corpus instead.

## ADR-010 Audit log
**Decision.** Append-only JSONL (`data/audit/audit-YYYY-MM.jsonl`), opened `O_APPEND`, fsync per record. Each record has `prev_sha256`, forming a hash chain, and the chain head is mirrored in the DB. `atlas audit verify` checks it. Fields: ts, scan_id, target, transport, op template (`atlas-probe docker`, `GET /api2/json/nodes/{node}/qemu`), status, duration_ms, bytes, refusal reason. There is no update/delete code path. Monthly rotation. The owner can ship it via the host's syslog/promtail if they want.
**Rejected.** DB-only (same blast radius as the data); remote syslog required (external dependency).

## ADR-011 Identity, snapshots and diff
**Decision.** Natural keys per SPEC §5. The snapshot is canonical JSON (sorted keys, normalized IPs/MACs, sorted set-like lists keyed by identity) hashed with SHA-256 and deduplicated. Volatile fields are declared on the model (`json_schema_extra={"volatile": True}`) and stripped before hashing, so an unchanged host produces no new snapshot. Events are derived by typed rules over the field-level diff (DeepDiff-style, own implementation for determinism).
**Rejected.** Diffing raw outputs (noisy, would require persisting unredacted data); generic DeepDiff with no model awareness (order noise, no typed events).

## ADR-012 Storage
**Decision.** SQLite in WAL mode via SQLAlchemy 2 (sync engine in a worker thread; async isn't needed at this scale). Portable types only, Alembic from the first table. The DB is sensitive: the volume lives on the encrypted VM disk, file mode 0600, and backups go through `atlas backup` (online `.backup`) for DEPLOY.md.
**Rejected.** Postgres in v1 (an extra service); SQLCipher (painful wheels on Windows; host-level encryption is enough for this threat model).

## ADR-013 Web UI and auth
**Decision.** Server-rendered Jinja2 + HTMX + Cytoscape.js (vendored; SHA-256 of each vendored file checked in a test). Strict CSP with per-request nonce, no inline handlers. Headers: HSTS (via proxy), X-Content-Type-Options, frame-ancestors 'none', Referrer-Policy same-origin (amended M7: with no-referrer, browsers send `Origin: null` on plain form POSTs, which the Origin check rightly rejects), COOP/CORP.
- Auth: local users, argon2id (argon2-cffi defaults or stronger), server-side sessions in the DB, cookie `__Host-atlas` with HttpOnly, Secure, SameSite=Strict, rotated on login, idle and absolute timeouts, login rate-limit/lockout.
- CSRF: synchronizer token per session on every non-GET request.
- OIDC: later, via authlib.
- `--insecure-http` only for localhost dev.

**Rejected.** SPA + JWT in localStorage; basic auth at the proxy only (no CSRF and no per-user audit).
**Implemented (M5).**
- **Passwords:** argon2-cffi `PasswordHasher` defaults (argon2id). Lockout after 5 failures for 15 min. Unknown users are verified against a dummy hash, so timing doesn't reveal valid names. There's also a per-client login throttle (20 attempts / 10 min).
- **Sessions:** server-side table storing only the SHA-256 of the token. 30 min idle, 12 h absolute. `set_password` ends all of that user's sessions.
- **CSRF:** a synchronizer token per session, sent as the `X-CSRF-Token` header (HTMX `hx-headers`) or a form field. Same-origin `Origin` check. The login form uses a double-submit `__Host-atlas-login` cookie.
- **Cookies:** `__Host-` prefix, Secure, HttpOnly, SameSite=Strict.
- **CSP:** `default-src 'none'`, scripts only `'self'` + per-response nonce, no `unsafe-inline`/`unsafe-eval`. `style-src 'self'` plus **one hash**: the fixed `<style>` cytoscape 3.34.4 injects (verified in the browser, no other violations).
- **htmx config:** `allowEval:false`, `allowScriptTags:false`, `selfRequestsOnly:true`.
- **Other headers and guards:** TrustedHost, `Cache-Control: no-store` on every non-static response, X-Frame-Options DENY, COOP/CORP, Permissions-Policy, optional HSTS (`--hsts` behind a TLS proxy).
- **Templates:** autoescape, and a test fails on any `|safe`.
- **Vendored JS:** htmx 2.0.11 and cytoscape 3.34.4 were taken from npm tarballs verified against the registry sha512 integrity, and their SHA-256s are pinned in a test (static/vendor/VENDOR.md).

## ADR-014 MCP server
**Facts.** The official Python SDK `mcp` has a 2.x stable line (mid-2026). 1.x is in maintenance. Verify the exact version on PyPI at M6.
**Decision.** Pin `mcp>=2,<3`. Tools are read-only query functions over the read models, with no scan trigger. Transports: stdio, and Streamable HTTP bound to the private interface behind the proxy, with a bearer token from a Docker secret (constant-time compare; 401 is not logged with the token). Result sizes are capped. Optional sanitize mode (THREAT-MODEL T-MCP).
**Rejected.** A custom JSON-RPC server; exposing an SQL tool (unbounded queries).

## ADR-015 Process model and scheduler
**Decision.** One container and one process: FastAPI (uvicorn) + APScheduler AsyncIOScheduler + MCP HTTP mounted as a sub-app. Scan lock = an OS file lock via `filelock` (cross-platform; already in the dependency tree), held for the whole scan; a DB lease can be added if multi-host workers ever appear. Pin APScheduler 3.11.x and re-check 4.x stability at M6.
**Rejected.** Celery/Redis (overkill); a separate worker container (more moving parts for ~100 targets).

## ADR-016 Unknown-device discovery is passive
**Decision.** Candidates come only from UniFi clients/devices, Proxmox, and ARP/NDP neighbour tables from already-probed hosts. No ICMP or port scans.
**Rejected.** Ping sweep / nmap: active, noisy toward IDS, outside the "read-only" spirit.

## ADR-017 Container image and supply chain
**Decision.** Multi-stage build: `ghcr.io/astral-sh/uv` builder → `python:3.12-slim-trixie` runtime, digest-pinned, non-root uid 10001, `read_only: true`, tmpfs `/tmp`, `cap_drop: [ALL]`, `no-new-privileges`, healthcheck. `uv.lock` with hashes. CI: ruff, mypy, pytest (ubuntu + windows), gitleaks, pip-audit, Trivy image scan, SBOM (syft), build + push to GHCR with provenance on `main` tags only. Dependabot for pip, actions and docker. Actions pinned by SHA.
**Rejected.** Distroless (harder debugging, little gain over slim with a non-root user and ro rootfs); Alpine (musl wheels for argon2/cryptography).

## ADR-018 Secrets handling
**Decision.** `SecretResolver` reads `/run/secrets/<name>` (prod) or `./secrets/<name>` (dev, git-ignored, never read by Claude). Values are wrapped in `SecretStr` and only unwrapped inside the transport call. SSH private keys are mounted read-only. Names must match `[a-z0-9][a-z0-9_.-]{0,63}`; symlinks, directories and files over 64 KiB are refused. The 0600 check applies to the dev `./secrets/` directory only, because Docker Compose bind-mounts file secrets 0444 and ignores `mode`, so `/run/secrets` relies on container isolation (non-root, single-purpose container). `.env.example` only. gitleaks runs in pre-commit (staged changes) and in CI (full history). Fake secrets must contain `ATLASFAKE`, the only allowlist.
**Rejected.** Env-var secrets (they leak via `/proc`, `docker inspect`, crash dumps); a Vault (an extra service for a homelab).

## ADR-019 Change-noise policy (M2)
**Context.** A diff is only useful if an unchanged host produces nothing.
**Decision.**
- **Volatile, never diffed:** uptime, pids, mount used/avail, interface operstate, service `sub`, neighbour (ARP/NDP) tables (kept for reconciliation in M4) and per-section errors.
- **Excluded:** `veth*` interfaces. They churn on every container restart, so only a volatile count is kept.
- **Set-like lists are keyed by identity** (sockets by proto/address/port, routes by family/dst/gateway/dev, packages by name, cron by source+line), so ordering never matters.
- **Packages:** a fixed key-package list (kernel, openssh, sudo, docker, systemd, openssl, libc, …) gets individual events. Every other package change is folded into one `packages.changed` event per host.
- **Cron:** reported per source file. Redaction markers are keyed by an HMAC, so a rotated secret in a cron line shows up as a change without being revealed.
- **Unclaimed changes:** anything no rule claims is folded into one `facts.changed` event, so nothing is silently dropped.
- **Reachability:** events fire on transitions only (`host.unreachable` / `host.recovered`), not on every failed scan.

**Rejected.** Generic JSON-path events (unreadable); diffing raw probe output (noisy, and it would need unredacted data).

## ADR-020 Entities, facets and parents (M3)
**Context.** One API call reports a whole cluster. One host carries several collectors' views.
**Decision.**
- **Facets.** A collector run returns `FacetResult`s: entity key, kind, display name, an optional model and an optional parent.
- **Snapshots.** Each `(entity, collector)` pair is a facet with its own snapshot and diff.
  - linux-ssh and docker both attach to `host:<machine-id>`.
  - The docker collector reads the probe `os` section only to learn that machine-id.
- **Model-less facets** (containers, compose projects) register entities for annotations and search. Their changes are diffed inside the parent facet, so no duplicate events.
- **Topology.** `entities.parent_key` records container→host, guest→node and node→cluster. Migrations update the parent.
- **Complete runs.** A run marked `complete` (the cluster list succeeded) retires facets it no longer reports: `entity.removed`, status `gone`.
- **entity.added** fires only for genuinely new entities, not for a second collector's first facet.
- **Collectors choose their own targets.** SSH collectors use hosts from hosts.yaml; the proxmox collector uses `sources.proxmox`.

**Rejected.** One entity per container with its own snapshot (an event storm on every compose update, and IDs churn). A single merged "host" document across collectors (a failure in one collector would blank the others).
**Known gap (M4).** The VM↔Linux-host link (by MAC) is not made yet, so `pve2 (PVE node)` and `pve2` (SSH) are separate entities. Both report the kernel upgrade.

## ADR-021 Correlation and unknown devices (M4)
**Decision.** A passive reconciliation pass runs after every scan (`engine/reconcile.py`).
- **Correlation.** An SSH host with a NIC MAC equal to a Proxmox guest NIC gets `same_as = pve:vm|lxc:…`. One whose IP equals a PVE node's cluster IP gets `same_as = pve:node:…`. Logical topology: node > VM (≡ host) > containers.
- **Known identities.** UniFi device MACs and NAS MACs, plus hosts.yaml `address` and `match.mac`.
- **Unknown devices.** Candidates are UniFi clients (with name, uplink AP or switch, IP) and ARP/NDP neighbours of probed hosts. A candidate is unknown if neither its MAC nor its IP is explained by any facet or hosts.yaml.
  - It becomes entity `net:mac:<mac>` with status `unknown`.
  - The VLAN comes from the UniFi network whose subnet contains the IP.
  - First sight emits `device.unknown_seen` ("new device on VLAN 30 via ap-office"). A later match emits `device.identified`.
- **Missing.** An inventory host whose last 3 runs all failed gets status `missing`; a success restores it.

**Rejected.** OUI vendor lookup (needs a downloaded database; possible later as a vendored file); active probing of unknowns (ADR-016); auto-adding unknowns to inventory (a human decision).
**Follow-up (M5).** Acknowledging an unknown device is an annotation (`acknowledged: true`), editable in the UI.

## ADR-022 Annotations: YAML is the source of truth (M5)
**Decision.**
- **Storage:** `annotations/*.yaml`, one file per entity, file name = slug(key) + sha256(key)[:10]. User input never chooses a path.
- **Writes:** atomic (temp file + replace), with a fixed key order so git diffs stay small.
- **Index:** the DB table `annotations` is rebuilt from YAML at UI start and after every save. Invalid files are skipped and listed on the dashboard.
- **Validation:** links must be http(s), tags are slug-like, criticality is an enum, `extra=forbid`.
- **Acknowledging an unknown device** writes `acknowledged: true` and sets the entity status to `acknowledged`. Reconciliation keeps that status.
- **Locations:** live mode uses `$ATLAS_CONFIG_DIR/annotations` (your private config repo). The demo lab copies `fixtures/demo-lab/annotations` to `data/demo-lab/annotations` on first `serve`, so UI edits never touch committed fixtures.

**Rejected.** DB as the source of truth (not git-friendly); one big YAML file (merge conflicts); free-form file names from the UI (path traversal).

## ADR-023 Scheduler, exports, sanitize and MCP as built (M6)
**Facts (checked 2026-10-18).**
- `uv add` resolved `apscheduler` 3.11.3 as the newest release under `<4` and `mcp` 2.3.0 from PyPI. APScheduler 3.x ships no type information, so mypy has a scoped `ignore_missing_imports` override for `apscheduler.*`.
- In `mcp` 2.x the high-level server is `mcp.server.mcpserver.MCPServer` (1.x called it `FastMCP`). `ToolAnnotations` takes snake_case fields (`read_only_hint`, ...), serialised as the spec's camelCase hints.
- The SDK's built-in HTTP auth is the OAuth resource-server flow. `streamable_http_app()` accepts `TransportSecuritySettings` for DNS-rebinding protection (Host/Origin allowlists).

**Decisions.**
- **Scheduler** (`homelab_atlas/scheduler.py`):
  - One APScheduler job per collector: `max_instances=1`, `coalesce=True`, ±10 % jitter, first runs staggered 5–60 s after start.
  - Intervals follow SPEC §9 and can be overridden with `ATLAS_INTERVAL_<COLLECTOR>` (`0` disables a collector, the minimum is 60 s).
  - Jobs are serialised in-process by an asyncio lock. Across processes, the engine's file lock applies: when `atlas scan` holds it, the job is retried in 120 s and does not count as a failure.
  - Backoff applies only when **every** target of a collector failed: the delay is interval × 2^n, capped at 6 h. One success resets it. A partial failure does not back off, because the healthy targets still need scanning.
  - Retention runs after each scheduled scan.
  - The scheduler starts only with `atlas serve --schedule`. A plain `serve` is a read-only viewer and `/scan` returns 404.
  - The dashboard "Scan now" is `POST /scan`, which requires login, the CSRF token and a same-origin request. It returns 202, or 200 with "already running" (htmx does not swap 4xx). A manual scan is the full scan, through the same engine and read-only choke points as `atlas scan`.
- **Retention** (`store/retention.py`, `atlas db prune --days N`, env `ATLAS_SNAPSHOT_DAYS`, default 90):
  - Snapshots of scans older than N days are deleted, except the newest per (entity, collector), which is the diff baseline.
  - Blobs no snapshot references are deleted.
  - Events are never pruned.
- **Exports** (`atlas export {json,csv,md,mkdocs,mermaid} [--sanitize] [-o DIR]`):
  - One JSON-able document (schema `atlas-export/1`) is built from the DB and rendered per format. Sanitising happens on that document before rendering, so every format gets identical treatment.
  - CSV cells starting with `= + - @`, tab or CR are prefixed with `'` (OWASP CSV injection).
  - Markdown and MkDocs output escapes all target data: HTML is escaped, Markdown metacharacters get backslashes, and newlines are folded. MkDocs renders raw HTML, so a container label like `<script>` or `[x](javascript:…)` must not reach a published site as markup. Mermaid and YAML nav labels go through their own character filter.
  - The MkDocs site is plain: `mkdocs-material` with mermaid via `pymdownx.superfences`.
- **Sanitize, deviating from SPEC §10's "documentation range" for IPv4.** The three IPv4 documentation /24s cannot hold a real lab's subnets, so each real /24 maps to a distinct keyed `10.X.Y.0/24` and the host octet is kept. Subnet membership and "same network" survive. For IPv6, each /64 maps into `2001:db8::/32` and the interface ID is hashed, because EUI-64 IIDs embed the MAC.
  - MACs become `02:` + keyed hash (locally administered). OUIs are not kept.
  - Names (entities, hostnames, SSIDs, clients, search domains) become `<kind>-NN`, numbered in sorted order.
  - Machine IDs and other 32-hex IDs are hashed.
  - Owner, purpose, notes, links, description, serial, comments and GECOS are dropped, and annotations are nulled.
  - A final regex pass rewrites any address or known name left inside free text.
  - The key is HMAC(installation redaction key, `atlas-sanitize/1`). Pseudonyms are therefore stable across exports (sanitised exports can be diffed) but not reversible without the key, and differ between installations.
  - Tests assert that no MAC, private or public IPv4, IPv6 or entity name from the real export appears in any sanitised format or MCP answer. Vendor model strings such as "UCG-Ultra" are allowed.
- **MCP** (`homelab_atlas/mcp_server.py`, `atlas mcp [--http] [--sanitize]`):
  - Seven tools, all annotated `readOnly`, `!destructive`, `idempotent`, `!openWorld`. Every tool returns one structured object. Lists are wrapped as `{count, items}` and capped at 500 rows and 200 kB (items trimmed, then facets elided, with `truncated: true`).
  - There is no scan, write or raw-SQL tool.
  - stdio is the default.
  - **Amends ADR-015:** HTTP runs as its own process (`atlas mcp --http`, the same image as a separate compose service) instead of a sub-app of the UI. This gives separate auth domains (bearer vs session cookie), the UI's CSP/TrustedHost/session middleware does not wrap JSON-RPC, and either can be left off.
  - The HTTP guard is a small ASGI wrapper: exact `Authorization: Bearer <token>`, `hmac.compare_digest`, a token of at least 32 chars, 401 with `WWW-Authenticate: Bearer`, and the token is never logged. The token comes from secret `mcp_token`. The demo lab writes a random one to `data/demo-lab/mcp-token.txt` (0600).
  - The SDK's DNS-rebinding protection is on, with a Host allowlist (`--allowed-host`) and no Origins. The default bind is 127.0.0.1.

**Rejected.** The SDK's OAuth server for a single-owner LAN tool (moving parts without benefit); a DB advisory-lock row in addition to the file lock (single host; revisit with remote workers); backoff on partial failure; pseudonyms per export (they break diffs between sanitised exports).

## ADR-024 Container image, compose and image CI as built (M7)
**Facts (resolved 2026-10-18 from the registries and the GitHub API, not from memory).**
- Base images:
  - `python:3.12-slim-trixie`, index digest `sha256:a6e34c59…` (Docker Hub, last updated 2026-10-09);
  - `ghcr.io/astral-sh/uv:0.13.1`, `sha256:4a1f3666…`, matching the local uv 0.13.1.
- Scanner: `aquasec/trivy:0.76.0`, `sha256:2416d1f7…`.
- Actions (latest releases, tag → commit):
  - `docker/setup-buildx-action` v4.4.1 `f87e5991`
  - `docker/metadata-action` v6.2.0 `dc802804`
  - `docker/build-push-action` v7.4.0 `c3c9e263`
  - `docker/login-action` v4.6.0 `dbcb8138`

**Decisions.**
- **Image.** The Dockerfile follows ADR-017:
  - A uv builder runs `uv sync --frozen --no-dev --no-editable` into `/opt/atlas`, with bytecode precompiled.
  - The runtime is `python:3.12-slim-trixie` (same digest) with root-owned code and uid/gid 10001. `/data` is the only writable path (a volume). Config comes from `/config` and secrets from `/run/secrets`.
  - Packaging was checked by installing the built wheel into a fresh venv and running a lab scan, an export and `selftest security` from outside the repo.
- **Build context.** `.dockerignore` is an allowlist (`pyproject.toml`, `uv.lock`, `README.md`, `src/`). Fixtures stay out of the image because their `ATLASFAKE` secrets would trip secret scanners and they are dev-only. Data, config, secrets and git history stay out too.
- **Health.** A new unauthenticated `GET /healthz` returns `ok` and touches no data and no DB. It is used by the Dockerfile `HEALTHCHECK`. `serve` now always accepts `localhost` and `127.0.0.1` as Host in addition to `--allowed-host`, so the in-container probe works behind a custom hostname. Loopback names can't be rebound from a remote browser.
- **Compose.**
  - Shared hardening: `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, `tmpfs /tmp` (`noexec,nosuid,nodev`), `pids_limit`, `mem_limit`, `init`, and log rotation.
  - The UI is published on `127.0.0.1` by default. `--allowed-host`, `--forwarded-allow-ips` and `--hsts` are wired from `.env`.
  - `config` is mounted read-only, with `config/annotations` read-write on top for the editor.
  - MCP is an opt-in profile that waits for the UI to be healthy, because the UI runs the migrations.
  - Secrets are Docker file secrets. Their host files must be owned by uid 10001, since compose ignores `mode`/`uid` for file secrets (see ADR-018).
- **Image CI** (`.github/workflows/image.yml`), in this order:
  1. Build with `load`.
  2. Smoke-test under the production flags: `--read-only`, `--cap-drop ALL`, `no-new-privileges`, uid 10001, `--network none`. The checks are `--version`, `selftest security`, "code not writable" and "container turns healthy".
  3. Run Trivy (vuln, secret and misconfig; fixable HIGH/CRITICAL fails the build).
  4. On `main`/`v*` only, log in to GHCR and push with `sbom: true` and `provenance: mode=max`.
- **CI permissions.** Default `contents: read`, plus `packages: write` on the image job only. Actions are pinned by commit SHA.
- **Trivy runs from its digest-pinned image** rather than `aquasecurity/trivy-action`. This is the same pattern as gitleaks: one pinned artifact, no composite action that pulls further code at run time.
- **Platform.** `linux/amd64` only for now: the deployment target is a Proxmox VM. arm64 can be added with QEMU if the collector ever runs on a Pi.
- **Dependabot** gains the `docker` ecosystem for the base-image digests.

**Rejected.** Distroless (ADR-017); baking the demo lab into the image (fake secrets, dev-only); running MCP-HTTP inside the UI process (ADR-023); signing with cosign keyless (BuildKit provenance and SBOM attestations cover the private-registry use case; revisit if images become public).

## ADR-025 Onboarding from the web UI: Targets page, encrypted vault, password SSH (owner request)
**Context.** The owner wants to add VMs in the UI, type the SSH login and the UniFi/Proxmox keys there, and have atlas log in and document everything, with no files to hand-write and nothing installed on the VMs. When asked how VMs should be reached, the owner chose **username + password** (2026-10-19).

**Decision.**
- **Targets page** (`/targets`):
  - Add, edit or remove machines and Proxmox/UniFi/UNAS sources.
  - Entries are written to an app-managed `<data>/inventory.yaml`, atomically and validated by the same strict models as `hosts.yaml`. It is merged with an optional `hosts.yaml`; `hosts.yaml` wins on name clashes and those entries are read-only in the UI.
  - A bare IP becomes the right API URL: `:8006/api2/json` for Proxmox, `/proxy/network/integration` for UniFi.
  - Each machine has **Test login**, which runs the `version` section, and **Scan**, a scan of that one target through the normal engine.
  - The scheduler object always exists, so these buttons work without `--schedule`.
- **Vault** (`security/vault.py`):
  - AES-256-GCM per secret, with the secret name as associated data. One JSON file, rewritten atomically, mode 0600.
  - The key comes from the Docker secret `atlas_master_key` (recommended, and required by the compose file). Failing that, a generated `<data>/master.key` is used.
  - Values are write-only in the UI: a form shows only *stored / missing*, and an empty field keeps the stored value.
  - Transports resolve secrets through `ChainedSecrets`: operator secrets (`/run/secrets`, `./secrets`) first, then the vault.
  - UI-entered secrets are named `ui-<kind>-<name>`.
  - Every change is audited with `transport="ui"`, recording names only.
- **Identity pinning without trust on first use** (`security/discover.py`):
  - "Fetch host key" and "Fetch certificate" read only the handshake identity; they neither authenticate nor send a request. They are audited.
  - The UI shows the fingerprint along with how to check it on the device. Pinning happens only after the owner ticks *I checked this fingerprint*.
  - Fetched certificates are stored in `<data>/ca/` and pinned as `ca_file` + `sha256_pin`, with `check_hostname: false` because consoles use self-signed IP certificates.
- **Password-mode SSH** (`SshTarget.auth="password"`):
  - The runner still accepts only `ProbeSection` enums.
  - The transport sends one **constant** loader per section, `bash -c '<INLINE_LOADER>' atlas <section>`, and streams atlas's **own bundled probe** (the same reviewed, read-only script as `docs/targets/atlas-probe`) on stdin. The first line of stdin is the sudo password, or empty when sudo is unticked.
  - The loader tries `sudo -n` first. Otherwise, if the password is accepted by `sudo -S -k true`, it pipes the password plus the probe to `sudo -S -k bash -s`. Otherwise it runs as the login user, so root-only sections degrade to partial.
  - The password travels only via stdin and bash builtins: never argv, never env, never logs or audit. Passwords containing a newline, a CR or a NUL are refused.
  - Host keys stay pinned, and every refusal happens before a connection exists, so a password is never offered to an unverified server.
  - Nothing is written on the target. Probe 1.3.0 reports `inline` instead of a file hash when streamed.
  - Verified locally against an in-process SSH server (exact wire command, exact stdin) and by running the loader with real bash (non-sudo path).
  - **Not yet verified on a real host:** the `sudo -S` path. It relies on sudo reading the password line from stdin before `bash -s` reads the rest.
- **Key mode** (ADR-002) stays available per machine and remains the strictest option.

**Consequences / risk accepted by the owner.**
- In password mode, read-only rests on atlas's code alone: there is no target-side gate. If the account has sudo, a compromised atlas could act as root on that VM.
- The vault protects against leaks of the vault file alone. Anyone with the data volume *and* the master key can decrypt it, which is why the master key should come from a Docker secret outside the volume.
- SECURITY.md lists both.

**Rejected.**
- Installing the probe over SSH from the UI: a write to the target, which violates "no changes to any target".
- Trust on first use for host keys and certificates without owner confirmation.
- Storing secrets in the DB or `inventory.yaml`.
- Showing stored secrets back.

## ADR-026 Deployable as-is: first-run account, built-in HTTPS, installer, SSH key option, UniFi cloud keys (owner request)
**Context.** The owner asked for a stack that is ready to deploy from GitHub, with:
- a script to run after pulling;
- logins created after cloning;
- both SSH options (simple username/password for local use, keys for people who want them);
- a UniFi integration that works with "the API key I have", following https://developer.ui.com/network/v10.6.106/gettingstarted.

**Decisions.**
- **No default password, ever.**
  - While no account exists, `serve` writes a one-time setup token to `<data>/setup-token.txt` (0600) and prints it in the log.
  - `/setup`, protected by login-CSRF, the token (constant-time compare) and the login throttle, creates the first account and logs it in. The token is then deleted and `/setup` closes for good.
  - `atlas user add --password-stdin` serves scripts, and `deploy/atlas.sh user add` creates accounts at any time.
- **Built-in HTTPS for LAN use.** The `__Host-` Secure cookies only survive over HTTPS, so on a LAN without a TLS proxy login would silently fail.
  - `serve --self-signed-tls` generates a per-install ECDSA P-256 certificate (10 years, SANs = `--allowed-host` names plus loopback) under `<data>/tls/` and prints its SHA-256.
  - HSTS stays off in this mode: it would stop browsers accepting the self-signed certificate after a reinstall.
  - The compose default is LAN mode on 8443. `docker-compose.proxy.yml` switches to HTTP on 8080 behind your own proxy, with HSTS and `--forwarded-allow-ips`.
  - `--allowed-host` accepts comma-separated values.
  - `atlas healthcheck` (security package, loopback only, `http.client`) probes `/healthz` over HTTPS or HTTP for the container HEALTHCHECK.
- **`deploy/atlas.sh`** provides `install`, `update`, `user add|passwd`, `status`, `logs`, `backup`, `stop|start` and `uninstall`. `install` does the following:
  - checks for docker and the compose plugin;
  - writes `/opt/atlas/{docker-compose*.yml,.env,secrets,config}`;
  - generates `atlas_master_key` (48 random bytes) and `mcp_token`;
  - detects the host's IPv4 addresses and names for the Host allowlist and the certificate;
  - `chown`s to uid 10001;
  - pulls the GHCR image, or builds it from the clone when the pull fails (private package, or no `docker login`);
  - asks for the first account and starts the stack;
  - waits for healthy and prints the URL and the certificate fingerprint.

  Passwords reach the container only on stdin. The script is tested against a fake `docker` that records every call (`tests/deploy`), and shellchecked in CI.
- **SSH options per machine (Targets form):**
  - *password* (ADR-025);
  - *atlas SSH key, nothing installed*: atlas generates one ed25519 key into the vault and shows only the public line to paste into `authorized_keys`;
  - *key + installed forced-command probe* (ADR-002, strictest).

  `SshTarget.probe` is `streamed` or `installed`. Password mode is always streamed.
- **UniFi: both kinds of key.** Facts were read on 2026-10-19 from developer.ui.com, using the Network v10.6.106 `llms.txt`, its OpenAPI `servers`, the "Connector - GET" page and Site Manager OpenAPI v1.0.0.
  - **Local key**, created in the Network app on the gateway: `https://<gateway>/proxy/network/integration`, header `X-API-KEY`, no internet needed. This stays the default and the recommendation.
  - **unifi.ui.com (Site Manager) key**, which is what the getting-started page describes ("Generate keys at unifi.ui.com"). It reaches the console only through Ubiquiti's cloud connector `https://api.ui.com/v1/connector/consoles/{id}/…` (console firmware ≥ 5.0.3, **100 requests/min per console**, 25 s timeout, 10 MB bodies).
    - The console id comes from Site Manager `GET /v1/hosts`, and consoles without the Network app are filtered out.
    - **The docs disagree on the proxied path.** The connector page's example is `…/consoles/{id}/network/integration/v1/sites`, and its "request flow" maps to `/proxy/<path>` on the console. The Network OpenAPI `servers` entry says `…/consoles/{consoleId}/proxy/network/integration`. Saving a cloud source therefore calls `GET /v1/info` on each form, connector page's first, and stores the one that answers.
    - Requests are paced at 0.75 s, under the limit.
    - This is an **opt-in cloud dependency**, a deliberate exception the owner asked for. Local keys don't touch the internet.
  - **Public-PKI TLS exception, for `api.ui.com` only** (`PUBLIC_PKI_HOSTS`): certifi bundle, host names always checked, refused for any other host. Every other source still needs a pinned anchor.
  - The base-path regex now allows `:` inside segments, as the console ids require.
  - The parser's fields were re-checked against the v10.6.106 OpenAPI: the client discriminator `type` is WIRED/WIRELESS/VPN/TELEPORT, and wired and wireless clients carry `macAddress`, `ipAddress` and `uplinkDeviceId`.
- **Source "Test connection"** does one GET of `/version` (Proxmox) or `/v1/info` (UniFi) with the stored credential.

**Rejected.**
- A default admin password, or a password printed in logs: the token proves server access instead.
- Always requiring a reverse proxy: too much for a single-owner LAN tool.
- Plain-HTTP cookies without `Secure` (session theft on shared Wi-Fi).
- Guessing which UniFi key type the owner has.
- Shipping only cloud mode: it adds an internet dependency that local keys avoid.

## ADR-027 Discovered devices: document infrastructure, not every phone (owner request)
**Context.** "It will find plenty of devices on the network, but it should only take the VMs, servers, rpi..."

**Decisions.**
- **Classification** (`engine/classify.py`, purely local heuristics, no lookups). Every unexplained device (UniFi client or ARP neighbour) gets a category: `vm`, `container`, `pi`, `nas`, `server`, `network`, `personal`, `iot` or `unknown`. The reasons are shown in the UI. Signals, strongest first:
  - **Vendor prefixes (OUI):** Proxmox `bc:24:11`, QEMU, VMware, Hyper-V, VirtualBox and Xen; Raspberry Pi `b8:27:eb dc:a6:32 e4:5f:01 28:cd:c1 d8:3a:dd 2c:cf:67`; Synology and QNAP; Docker `02:42`.
  - **Randomized MACs** (locally administered bit) mean a personal device.
  - **Name hints:** consumer words (iphone, android, tv, printer…) vs server words (pve, nas, docker, pihole, homeassistant…).
  - **Wired on a server/lab/mgmt VLAN** means a server.
  - **Wireless with no hint** means a personal device. A wired device with no hint stays `unknown` and is listed.
- **What the UI shows:**
  - The Unknown page lists infrastructure and `unknown` by default. Phones, TVs and IoT sit behind "show everything".
  - Infrastructure rows get **Add as target**, which pre-fills the VM form with name, IP and type (Pi → Linux + Pi collectors).
  - New personal/IoT devices raise `info` events instead of `notice`, so the changelog isn't flooded.
- **Guest IPs from UniFi:**
  - Reconciliation writes a "seen on the network" facet onto every Proxmox VM/LXC whose NIC MAC UniFi sees: IP, network/VLAN and uplink switch/AP, with all NICs listed.
  - VMs without the QEMU guest agent therefore still show IPs, VLANs and their switch on the host page, in the topology, in exports and in MCP answers.

**Rejected.** Active scanning or fingerprinting (ADR-016 passive only); vendor lookups over the internet; hiding devices outright (they're one click away, and the owner decides).

## ADR-028 Proxmox VE over SSH: guests from /etc/pve when there is no API token (v2, owner request)
**Context.** The owner added their PVE node as an SSH machine but no Proxmox API source, so the dashboard showed no nodes and no VMs. "I want the topology of the two Proxmox and which VMs they cover."

**Facts used.** From the Proxmox VE Administration Guide, chapter "Proxmox Cluster File System (pmxcfs)", for version 9.2.13 (read 2026-10-19):
- Guest configs live in `/etc/pve/nodes/<node>/qemu-server/<vmid>.conf` and `/etc/pve/nodes/<node>/lxc/<vmid>.conf`.
- `.members` and `.vmlist` are status files. The guide says they are JSON but gives no schema, so the parser is lenient and tolerates missing keys.
- `/etc/pve/priv/` holds `authkey.key`, `token.cfg`, `shadow.cfg` and storage passwords. It is root-only.
- Group `www-data` can read most of the other files.

**Decisions.**
- Probe 1.4.0 gains a `pve` section that reads exactly these files:
  - `pveversion`;
  - `.members` and `.vmlist`;
  - the `qemu-server/*.conf` and `lxc/*.conf` globs;
  - `ls /run/qemu-server` and `/sys/fs/cgroup/lxc` for the running state.
- **`priv/` is never read.** The paths are constants in the probe, and a test fails if `priv` appears in them.
- Config values go through the Redactor, as for every collector. `cipassword` and similar fields are redacted.
- The parser stops at the first `[snapshot]` section, so only the current config counts.
- The linux-ssh collector emits `pve-node` and `pve-vm`/`pve-lxc` facets under the **same entity keys as the API collector**: `pve:node:{cluster}/{node}` and `pve:{vm|lxc}:{cluster}/{vmid}`. Each node emits itself and the guests in its own `nodes/<self>/` directory.
- `cluster_guests` (volatile) lets reconciliation claim the MACs and names of guests on nodes that aren't scanned yet. The topology then shows them as "not documented" placeholders under the right node.
- The SSH path is skipped when a Proxmox API source exists. The API stays authoritative and the two never fight over a key.
- A new `procs` section adds `ps` with fixed columns, args only. Command lines are redacted, at most 600 rows are kept, kernel threads are dropped, and it is volatile (never diffed).
- When `systemctl --output=json` is unavailable, a plain-text `list-units` fallback is used.

**Rejected.**
- Running `qm`/`pct` commands: they need root and widen the allowlist.
- Reading `/etc/pve/priv` or `storage.cfg` secrets.
- Calling the local API with a ticket over SSH: that is a credential on the wire.

## ADR-029 What runs where: app recognition and the Running views (v2, owner request)
**Context.** "Check everything that is running on the VMs, not only Dockers, but also services… especially in the Pi-hole."

**Decisions.**
- **`engine/apps.py`** is a static catalog of about 70 apps. Each entry has systemd unit prefixes, process names, container image substrings, well-known ports and a web UI port. Catalog entries cover:
  - DNS, VPN, remote access, proxies;
  - hypervisor and containers;
  - home automation, media, files;
  - automation, dev, monitoring, databases;
  - system apps.
- **Evidence rules.** A unit, process or image is required. A listening port alone is weak evidence and never identifies an app; it is only added as supporting evidence.
- **Web UI link.** It is offered only when the web port is actually listening, or when there is no socket list at all.
- **Computed on read, never stored.** Recognition runs when a page loads, so improving the catalog changes old scans too and needs no migration.
- **Machines read model (`web/views.py`).** One card per box. A Proxmox guest and the Linux host inside it are merged through `same_as`. Each card carries its services, containers, ports and apps.
- **Where it shows up:**
  - the `/running` page (all machines, searchable);
  - a Running panel on host pages (tabs: services, containers, processes, ports, timers);
  - dashboard cards;
  - topology panels.
- **IP table: one row per device.** Rows are grouped by entity. Link-local, loopback and container-bridge addresses (`docker*`, `br-*`, `veth*`…) are hidden behind a link. A stale "unknown device" row is dropped when the same MAC belongs to a documented entity.

**Rejected.**
- Storing app detections as facets: they would raise diff noise every time the catalog changed.
- Fingerprinting by connecting to ports: that is active probing, which ADR-016 rules out.

## ADR-030 Topology v2: Proxmox-first, interactive (v2, owner request)
**Context.** "The topology of the two Proxmox and which VMs they cover… interactive, right click… effects… better looking."

**Decisions.**
- **The logical view is now "Proxmox":**
  - compound boxes go cluster → node → guests;
  - an "Other machines" group holds Pis, NAS and bare-metal hosts;
  - containers are separate nodes, hidden by default, linked by a dashed "runs" edge and placed inside their machine's node box.
- **Tidy layout.** A deterministic preset layout places guests in rows. Each row is as tall as the tallest container stack under it, so nothing overlaps; a test checks this in the browser, and the read model is checked in `tests/web/test_v2_pages.py`. Organic (cose) and Rings (concentric) are offered as alternatives.
- **Interaction:**
  - hover highlights neighbours;
  - click opens a side panel;
  - double-click opens the host page;
  - right-click menu: open, open web UI, copy IP, focus, highlight, show/hide containers, hide, add as target;
  - background menu: fit, re-arrange, show hidden, PNG, scan everything (POST with the CSRF header);
  - search, plus toggles for containers and undocumented machines.
- **Rendering:**
  - status borders and a glow underlay;
  - animated dashes on uplinks and "runs" edges, disabled under `prefers-reduced-motion`;
  - SVG data-URI icons, which the CSP allows (`img-src 'self' data:`);
  - name and IP as two label lines.
  - Panel text is set with `textContent` only, so there is no HTML from target data.
- **Visibility.** Layout code uses its own check (the `gone-hidden` class on the element or an ancestor). Cytoscape's `visible()` is stale right after a class toggle in a batch, which placed newly shown containers wrongly.
- **Updates.** `atlas update` does a `git pull --ff-only` of the clone, writes a pre-update backup (the last 5 are kept), pulls the image and restarts. A `/usr/local/bin/atlas` shortcut makes this one command. The data volume, `.env`, `secrets/` and `config/` are never touched.

**Rejected.**
- A WebGL or 3D graph library: a bigger vendored surface for little gain.
- Free-form saved positions: the layout would no longer be reproducible, and they could be added later.
- Auto-updating from inside the container (watchtower-style): it needs the Docker socket inside atlas.

## ADR-031 Proxmox facts from three sources, one view (v3, supersedes the "API wins, SSH skipped" rule of ADR-028)
**Context.** On a real lab the owner had configured an API source whose token saw nothing, and ADR-028 then skipped the SSH path entirely. The result was no nodes and no VMs. A node's `/etc/pve` is the cluster file system: one node holds every node's guest configs (pmxcfs, PVE 9.2 admin guide).

**Decisions.**
- **Three facet names, all kept.**
  - `proxmox`: the API.
  - `pve-ssh`: a node about itself and its own guests, with running state from `/run/qemu-server` and the lxc cgroups.
  - `pve-ssh-peer`: a node's view of the other nodes and their guests. Config only, with status `unknown`.
  - `FacetResult.store_as` stores a facet under a name other than the collector's. A collector declares its `extra_facets`, so stale facets are removed per target and per facet name.
- **One view for readers.** `store.facets.facet_views()` collapses the three into a single `proxmox` facet, the strongest present (API > pve-ssh > pve-ssh-peer), with `source` kept for the UI ("from the node over SSH"). The UI, exports and MCP never see duplicates.
- **Events come from the strongest source only** (`ScanEngine._speaks_for`). Peers never raise events, and pve-ssh doesn't when an API facet exists. The demo lab's A→B golden diff is unchanged.
- **A token that sees nothing is diagnosed.** If `/cluster/status` and `/cluster/resources` return nothing, the run is `partial` and the error says to give the *token* the PVEAuditor role. The run is not `complete`, so an empty answer never marks guests as removed. Test connection also counts the nodes and guests the token can see.

**Rejected.**
- Keeping "API wins, SSH skipped": a misconfigured token hides the whole cluster.
- Writing SSH data under the `proxmox` name: the two sources would overwrite each other on every scan.
- Inventing running state for peer guests.

## ADR-032 Scans are queued, never dropped; every target shows its latest result (v3)
**Context.** "I have added all of them as targets, and they were discovered already", yet only 3 of 11 machines were documented. Two causes:
- `Scheduler.trigger()` returned "already running" and dropped the request, so clicking Scan on several machines scanned one.
- "Needs attention" only read the last scan, usually a one-collector scheduled run, so the failures were invisible.

**Decisions.**
- **A manual-scan queue.** Host requests are merged into a set, a full scan absorbs them, and a single worker drains the queue behind the scan lock. When `atlas scan` holds the file lock, the work is put back and retried after 30 s. `trigger()` returns `started` or `queued`.
- **Saving a host or a source queues its first scan.**
- **`queries.latest_runs()`**: the newest `CollectorRun` per (target, collector) across scans, with the time of the last good run.
  - The dashboard lists failed, partial and never-scanned *current* targets with their first error.
  - Targets has a **Last scan** column: health pill, age, and an expandable error per collector.
  - The "seen on the network" list leaves out addresses and names that are already targets.

**Rejected.**
- Running concurrent scans: SQLite has one writer, and the file lock is shared with the CLI.
- Making the button wait for the scan: scans take minutes.

## ADR-033 UI v3: Proxmox flow topology, Services table, menus, docs, license (v3, owner request)
**Context.** "pve1 has those VMs inside, pve2 has those VMs inside… like ProxMenux… more and better menus… a documentation page… a star favicon… all the services from all the VMs in a table we can filter… export it as CSV… publish-ready."

**Decisions.**
- **ProxMenux was studied, not copied.**
  - ProxMenux is GPL-3.0 and its monitor is Next.js/React/Tailwind; atlas is Jinja, htmx and Cytoscape, MIT. Copying code would force a relicence and doesn't fit the stack.
  - We reimplemented its ideas: a node → bridge → guest network flow, round kind-coloured nodes, traffic pulses, and KPI cards for guests and allocated vCPU/RAM. The README credits the inspiration.
- **Proxmox topology.**
  - Layout:
    - one compound box per node;
    - inside it, the hub (the node), its bridges (API `type=bridge` interfaces, or the host's `vmbr*` and `vnet*`), and its guests;
    - each guest is wired to the bridge its first NIC uses (`nic2` dashed for extra NICs);
    - a bus under each bridge, odd rows shifted half a column so drops pass between guests;
    - containers stack under their guest.
  - Implementation details:
    - classes are applied before the graph is created, so nothing animates from default sizes;
    - our own `shown()` replaces Cytoscape's lagging `visible()` in layouts;
    - node data never carries `source` or `target` keys, which Cytoscape reads as an edge (a test guards this).
- **Services page (`/services`, `/services.csv`).** One row per systemd unit or container on every documented machine.
  - Columns: machine, kind, node, IP, type, name, description, state, sub-state, enabled/restart, app, category, image and ports.
  - Filters are server-side (machine, state, type, text) and shared by the htmx table and the CSV export, so the export is exactly what you see.
  - CSV cells starting `= + - @` (and the other formula starts) are prefixed with `'`, the same as the exports.
- **Menus.**
  - Grouped `<details>` dropdowns (Infrastructure, Network), keyboard-closable, working without JS.
  - A Ctrl+K quick find over pages, machines and apps (`/api/palette`, same-origin links only).
  - Topology context menus gain scan-this-machine, copy MAC / SSH command, show only this, all containers on a node, and labels on/off.
- **In-app docs (`/docs`)** cover onboarding, Proxmox (SSH and token, including the privilege-separation step), UniFi, what is read, pages, shortcuts, updating, troubleshooting and security.
- **Publishing.**
  - The MIT license: permissive, and the norm for homelab tools.
  - CONTRIBUTING (the hard rules from CLAUDE.md, for humans), a short code of conduct, issue forms that warn against pasting secrets, a PR checklist and a CHANGELOG.
  - Version 0.3.0.

**Rejected.**
- GPL-3.0 to allow copying ProxMenux code: it would relicense a project whose own code is MIT-compatible, for little gain.
- Client-side-only filtering of thousands of rows.
- A separate SPA.

## ADR-034 Unrecognised ports and owner-defined app rules (v4)
**Context.** The app catalog will never know every self-hosted app. Scanopy's "unclaimed ports" and Homelable's pending list show the pattern: put the unknowns in front of the owner and let them name each one once. (Researched 2026-10-21: noted.lol articles on Homelable (2026-10-17) and Scanopy (2026-03-03), virtualizationhowto.com Scanopy review (2025-12).)

**Decisions.**
- **`views.unrecognised_ports()`** lists the sockets on documented machines that no detected app explains, and skips the rest:
  - ports a found app claims, or whose process is one of its process names;
  - loopback listeners;
  - a short list of plumbing ports (DHCP, rpcbind, NTP, mDNS, SSDP, NetBIOS);
  - `docker-proxy` ports published by a container an app already claims.
- Groups are keyed by what would identify the app:
  - a **container image** (a `docker-proxy` port mapped to an unknown container);
  - a **process name**;
  - for generic processes (`python3`, `node`, `java`, `docker-proxy` without a mapping…), the **port on that machine**.
- **Owner rules** (`engine.apps.CustomRule`) are stored in `custom-apps.yaml` in the data volume:
  - the model is strict pydantic with `extra=forbid` and bounded lists;
  - matchers are limited to `[A-Za-z0-9._@/+:-]`, names have no control characters or `<>`, and categories come from a fixed list;
  - writes are atomic (`0600`);
  - the file is re-read on mtime change; invalid entries are skipped and logged, and an unreadable file is ignored.
- `catalog()` = built-ins + owner rules. An owner rule with a built-in's name replaces it.
- Two new rule fields:
  - `strong_ports`: a port alone is evidence;
  - `hosts`: limit a rule to some machines. `detect()` takes the machine name.
- Port-only rules are always limited to the machines they were named on, so "python3 on 5000" on a Pi doesn't label every port 5000 in the lab.
- Only atlas's own data changes. Targets are never contacted. The form needs CSRF, like every POST.

**Rejected.**
- Active service fingerprinting (banner grabs): that is probing, which ADR-016 rules out.
- A community-wide rules registry: possible later as a file people share.

## ADR-035 UI v4: exports and diagnostics in the browser, change filters, saved layouts (v4)
**Context.** A full review of the UI, plus research ideas: exportable documentation (a recurring Reddit ask), "what changed" views, saved diagram layouts (Scanopy), and the need for a support path when atlas runs on a lab we can't see.

**Decisions.**
- **Exports page** (`/exports`, `/export/{md,csv,json,mermaid}`): the same builders as `atlas export`, served as downloads.
  - `?sanitize=true` uses the CLI's derived key (`cli_export.sanitize_key`), so pseudonyms are stable across CLI and UI.
  - Login required. CSV is zipped in memory.
- **Diagnostics** (`/diagnostics`, `/diagnostics/report`): versions, row counts, DB size, the scheduler (intervals, last status, backoff, queue), each target's latest runs and errors, and recent scans. The audit-chain check runs only for the downloaded report, since it walks the whole log.
  - The report has no secrets, which never reach the DB. It does list target names and IPs, and the page says so.
- **Changes**:
  - `since` (24h/7d/30d) and `machine` filters;
  - `queries.related_keys()` gives a machine, its `same_as` twin and their children, so containers count;
  - a severity/type summary;
  - `/changes.csv` with the same filters, formula-safe.
- **Topology layouts.** Dragged positions are stored per view in `localStorage`:
  - they are a per-browser convenience, not shared state;
  - they are applied over the tidy layout only;
  - containers follow a moved host;
  - Lock and Reset live in the background menu;
  - `?focus=` opens the graph on one machine.
- **Templates** use a Jinja `finalize` that renders None as blank and booleans as yes/no on every page. No template writes booleans into form values (checked).
- **`/docs` is public**: it is a static guide reachable from the login page. Everything else still needs a session.
- **Targets**:
  - a health tally;
  - `/targets/scan-many` (`failed` = failed or never scanned; `all`) queues through the scheduler's merge queue.

**Rejected.**
- Server-side shared layouts: they'd need write APIs and conflict handling, for one owner.
- A public share link for exports: atlas holds a map of the network, so downloads stay behind login.
