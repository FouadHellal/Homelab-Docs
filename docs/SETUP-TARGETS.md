# Setting up targets (least privilege, read-only)

atlas never changes a target. Everything below is a one-time setup **you** run on each target.
It creates an account that *can only read*, so the read-only guarantee does not rest on atlas's
code alone (THREAT-MODEL §B2/B3; ADR-002, -004, -005, -006).

> **Quick path:** you can skip most of this page. On the web UI's **Targets** page, add a VM
> with an SSH username and password; atlas then streams its read-only probe over the session
> and installs nothing (ADR-025). You still need the Proxmox token (§4) and the UniFi key (§5),
> pasted into the same page. Doing §2 instead, with an SSH key, an installed probe and the
> forced-command gate, is the strictest setup: read-only is then enforced on the VM itself and
> not only by atlas.

After each step, run `atlas doctor`. It connects with exactly these credentials and says what
works, what is missing, and whether anything has **more** privilege than it should.

## 1. Collector SSH key and secrets layout

Do this on the **deploy host** (the VM/LXC that runs the atlas container), not on a workstation.

```bash
mkdir -p secrets config/annotations && chmod 700 secrets
ssh-keygen -t ed25519 -N '' -C atlas-collector -f secrets/ssh_atlas_ro
mv secrets/ssh_atlas_ro.pub ssh_atlas_ro.pub      # public half: goes into authorized_keys
```

- One file per secret, named exactly as in `hosts.yaml` (`key:`, `credential:`). The file holds
  only the value, with no `KEY=` prefix.
- The container runs as uid 10001. Run `sudo chown 10001:10001 secrets/* && sudo chmod 0400 secrets/*`.
- Secrets are never in git, never in `hosts.yaml`, and never passed as env vars or CLI arguments.
  `hosts.yaml` holds secret **names**; validation rejects anything that looks like a value.

## 2. Debian/Ubuntu hosts (linux-ssh, docker)

Requirements: Debian 12+/Ubuntu 22.04+, systemd ≥ 246, iproute2, util-linux, dpkg, bash.
The files come from [`docs/targets/`](targets/), generated by `atlas targets render`. Review them first:
they are short and have no network access, no writes and no free-form arguments.

```bash
# on each target, as root (copy docs/targets/* over first, e.g. with scp)
useradd --system --create-home --shell /bin/bash atlas-ro
passwd -l atlas-ro                                   # no password login, ever
install -o root -g root -m 0755 atlas-probe       /usr/local/libexec/atlas-probe
install -o root -g root -m 0755 atlas-probe-gate  /usr/local/libexec/atlas-probe-gate
install -o root -g root -m 0440 sudoers.atlas-ro  /etc/sudoers.d/atlas-ro
visudo -cf /etc/sudoers.d/atlas-ro                   # must print "parsed OK"
install -d -o atlas-ro -g atlas-ro -m 0700 ~atlas-ro/.ssh
# authorized_keys: one line, from authorized_keys.example, with your collector IP and public key
printf '%s\n' 'restrict,from="10.0.10.50",command="/usr/local/libexec/atlas-probe-gate" ssh-ed25519 AAAA... atlas-collector' \
  > ~atlas-ro/.ssh/authorized_keys
chown atlas-ro:atlas-ro ~atlas-ro/.ssh/authorized_keys && chmod 0600 ~atlas-ro/.ssh/authorized_keys
sha256sum /usr/local/libexec/atlas-probe*            # compare with docs/targets/README.md
```

What this grants:
- `restrict` turns off PTY, agent, port and X11 forwarding and `~/.ssh/rc`.
- `from=` limits the key to the collector's address.
- The forced command means the client cannot run anything else. The gate accepts only
  `atlas-probe <section>` for a fixed list of sections, exact string match, and logs anything
  else to syslog.
- sudo allows exactly `/usr/local/libexec/atlas-probe <section>` and nothing else.
- **Do not** add `atlas-ro` to the `docker` group: it is root-equivalent. The probe reads Docker
  through sudo and strips env values **on the target**, so only variable names leave the host.
- Without the sudoers file the probe still works, but `ports` loses process owners and `docker`
  and root crontabs are empty (results show as `partial`).

Host key pinning: atlas trusts only the keys in `hosts.yaml` (no TOFU, no `known_hosts`).
Get the key, and **check its fingerprint on the host's console**, not over the same network path:

```bash
ssh-keyscan -t ed25519 10.0.20.11 2>/dev/null          # from the deploy host
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub        # on the target's console: must match
```

Updating the probe: when `atlas doctor` reports `probe outdated`, re-run `atlas targets render`,
review the diff, and reinstall `atlas-probe` (plus the gate and sudoers file, if they changed).

## 3. Raspberry Pi

Same as §2 (Raspberry Pi OS Bookworm or newer), plus `collectors: [linux-ssh, pi]` in `hosts.yaml`.
The `pi` section reads `vcgencmd` (temperature, throttling, firmware) and the device-tree model.
Add `docker` too if the Pi runs containers.

## 4. Proxmox VE (API token, PVEAuditor)

On one node (cluster-wide), as root:

```bash
pveum user add atlas@pve --comment "atlas read-only collector"
pveum acl modify / --users atlas@pve --roles PVEAuditor
pveum user token add atlas@pve collector --privsep 1      # prints the secret ONCE
pveum acl modify / --tokens 'atlas@pve!collector' --roles PVEAuditor
```

- Write the token as `atlas@pve!collector=<uuid-secret>` to `secrets/proxmox_auditor`.
- `privsep 1` makes the token's rights the intersection of the user's and the token's ACLs.
- PVEAuditor holds only `*.Audit` privileges, including `VM.GuestAgent.Audit` on PVE 9, which
  is needed for guest IPs and OS info. It cannot start, stop or reconfigure anything, and cannot
  use the guest agent's exec or file calls.
- `atlas doctor` reads `GET /access/permissions` and **fails if the token holds any non-Audit
  privilege**.
- TLS: copy the cluster CA (`/etc/pve/pve-root-ca.pem`) to `config/` and reference it as
  `tls.ca_file`. Optionally pin the node's leaf certificate with
  `tls.sha256_pin: <sha256 of the DER cert>`.
- No PBS: the collector reports "not backed up" guests (from `/cluster/backup-info/not-backed-up`)
  as findings.

## 5. UniFi gateway (UCG, Integration API key)

There are two kinds of key; the Targets page supports both (ADR-026):
- **Local key**, created in the UniFi Network app on the gateway (its integrations / API key
  settings). atlas talks to `https://<gateway>/proxy/network/integration` directly, with no
  internet. Recommended; the steps below are for this one.
- **unifi.ui.com key**, created in Site Manager (unifi.ui.com → Settings → API Keys). atlas finds
  your console with Site Manager `GET /v1/hosts` and goes through Ubiquiti's cloud connector
  (`api.ui.com`, 100 requests/min per console). Choose *unifi.ui.com key* in the form, click
  **Find my consoles** and pick your gateway. There is no certificate step: `api.ui.com` is
  verified against the public CAs.

Requires Network ≥ 9.3.
1. In UniFi OS, create a **local** admin (no cloud SSO), e.g. `atlas-view`, with **Network: View
   Only** and no other app access.
2. Sign in as that admin and create an API key in the Network application's integrations
   (API key) settings; the menu location moves between Network versions. Write it to
   `secrets/unifi_api_key`.
3. Export the console's certificate (or its CA) to `config/ucg.pem` and reference it as
   `tls.ca_file` (always required). The UCG's self-signed certificate usually lacks the
   hostname, so set `check_hostname: false` and add `sha256_pin` to bind the exact certificate.

> **Limitation (see SECURITY.md).** UniFi API keys have **no read-only scope**: a key carries
> the permissions of the admin who created it. Creating it as a view-only admin is the only
> target-side control. If your firmware won't let a view-only admin create keys, the key is
> admin-capable. atlas then relies on its code-side guard (GET-only allowlist, every `/actions`
> path denied) and on the key living only in a Docker secret. `atlas doctor` cannot verify key
> scope and says so.

Wi-Fi passphrases are never read: the per-SSID details endpoint is not on the allowlist, and
the redactor would mask `passphrase`/`psk` fields anyway.

## 6. UNAS (best effort)

There is no official UNAS API. Choose one:
- **`drive_api: true`**: a Drive API key (see the community docs in DECISIONS ADR-006) in
  `secrets/unas_api_key`, plus the
  certificate as for the UCG. atlas makes three GET calls (system, storage, device info) and
  treats every field as optional. These endpoints are community-documented, not official.
- **Manual**: `config/manual/unas.yaml` with `model`, `mac`, `firmware`, `pools`, `disks`, `shares`.

No SSH to the UNAS: Ubiquiti discourages it, and atlas doesn't need it.

## 7. hosts.yaml

`config/hosts.yaml`. Strict: unknown keys, duplicates and anything that looks like a secret
value are errors.

```yaml
version: 1
defaults:
  ssh: { user: atlas-ro, key: ssh_atlas_ro }       # secret NAME
sources:
  proxmox:
    - name: homelab
      url: "https://pve1.home.arpa:8006/api2/json"
      credential: proxmox_auditor
      tls: { ca_file: pve-root-ca.pem }
  unifi:
    - name: ucg
      url: "https://192.168.1.1/proxy/network/integration"
      credential: unifi_api_key
      tls: { ca_file: ucg.pem, check_hostname: false }
  unas:
    - name: unas
      manual: unas.yaml
hosts:
  - name: pve1
    address: 10.0.10.11
    type: proxmox-node
    collectors: [linux-ssh]
    ssh: { host_keys: ["ssh-ed25519 AAAA... pve1"] }
  - name: docker01
    address: 10.0.20.11
    type: linux
    collectors: [linux-ssh, docker]
    ssh: { host_keys: ["ssh-ed25519 AAAA... docker01"] }
  - name: pi-dns
    address: 10.0.20.53
    type: pi
    collectors: [linux-ssh, pi]
    ssh: { host_keys: ["ssh-ed25519 AAAA... pi-dns"] }
```

VMs and LXCs don't need entries to be inventoried: Proxmox lists them. Add a host entry only for
machines you want SSH facts from. A VM with an entry is correlated with its Proxmox guest
(`same_as`). Anything on the network that no entry or source explains appears under
**Unknown devices**.

## 8. Verify

```bash
docker compose run --rm atlas atlas doctor --live   # every target: reachability, probe hash, privileges
docker compose run --rm atlas atlas scan --live     # first scan
docker compose run --rm atlas atlas audit verify    # hash chain of every outbound call
```

Checklist:
- `doctor` shows **no** `excess privilege`, `probe outdated` or `host key` errors.
- On a Linux target, `sudo -l -U atlas-ro` lists only the `atlas-probe` lines.
- On a Linux target, `ssh -i secrets/ssh_atlas_ro atlas-ro@<host> id` is **refused** by the gate
  (exit 64, logged in syslog/journal as `atlas-probe-gate`).
- `atlas audit verify` passes, and the audit log grows by one record per outbound call.
