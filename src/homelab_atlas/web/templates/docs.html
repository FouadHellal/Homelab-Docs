atlas documentation

atlas documents your homelab and only ever reads. It logs in to your machines and controllers, records what runs where, links it all into a topology, and keeps a change history. It never changes anything on a target.

Getting started

  1. Add a Proxmox source or a Proxmox node on Targets, so atlas knows your nodes and every VM and LXC (how).
  2. Add your UniFi gateway, so atlas knows every device's IP, VLAN and switch port (how).
  3. Add your VMs, servers and Pis with an SSH login, so atlas can see what runs inside them (how).
  4. Each target is scanned as soon as you save it, then on a schedule. Watch the Last scan column on Targets.

Add your machines

Targets → Machines → + add a VM / host. Pick the type: linux, proxmox-node or pi. Then choose what to collect: linux-ssh for services, processes, ports, packages, users, disks and cron, docker for containers and compose projects, and pi for temperature and throttling.

Press Fetch host key, compare the fingerprint with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the machine, tick the box, and save. Test login checks the login. Scan queues a scan; nothing is dropped if another scan is running.

The Last scan column shows each target's latest result: ok, partial (usually no sudo), failed (open the line for the reason), or not scanned yet.

root logins are refused. Use a normal user, with sudo if you want Docker details.

Proxmox VE

There are two ways to document Proxmox. They work together, and you can use both.

A. Over SSH (no token)

Add each Proxmox node on Targets with type proxmox-node and use for sudo ticked. atlas reads the cluster file system /etc/pve: cluster members, every guest's configuration (name, cores, memory, disks, NICs, bridge, VLAN), and which guests are running on that node.

  • One node is enough to see the whole cluster. /etc/pve is shared, so every VM and LXC appears under its node. Add every node to also see each guest's running state.
  • /etc/pve/priv (keys, API tokens, passwords) is never read.

B. API token (read-only)

  1. Datacenter → Permissions → Users → Add, for example atlas@pve.
  2. Datacenter → Permissions → API Tokens → Add for that user. Keep Privilege Separation ticked.
  3. Datacenter → Permissions → Add → API Token Permission: path /, the token, role PVEAuditor, propagate. This is the step most people miss. With privilege separation on, the token itself needs the role, not only the user.
  4. On Targets → Proxmox VE → + add: URL https://<node>:8006/api2/json, the token as user@realm!tokenid=secret, then fetch and confirm the certificate.

Test connection reports how many nodes and guests the token can see. "sees no nodes" means step 3 is missing. The API adds backups, HA and guest-agent IPs. Where both sources exist, atlas shows the API's data and keeps the SSH data as a fallback.

UniFi

  • Local key (recommended): in the UniFi Network app on your gateway, open its integrations / API key settings and create a key. URL: https://<gateway>/proxy/network/integration. It needs no internet.
  • Cloud key from unifi.ui.com: pick cloud on the form and atlas finds your console. Requests go through Ubiquiti's connector.

UniFi gives every device's IP, VLAN and uplink. atlas matches Proxmox guests by MAC, so VMs without the QEMU guest agent still get an IP and a switch port.

What atlas reads

Machines (SSH)

OS and kernel, interfaces and routes, listening ports, disks, every systemd service (running, stopped, failed), running processes, timers, cron, users, packages. With sudo it also reads Docker containers, images, networks, volumes and compose projects.

Proxmox

Nodes, VMs and LXCs, cores, memory, disks, NICs, bridges and VLAN tags, running state. The API also gives backup jobs, guests without a backup, and HA.

UniFi

Gateway, switches, APs, clients, networks and VLANs, Wi-Fi SSIDs (never their keys).

About 70 common apps are recognised from services, processes, container images and ports, so a Pi-hole installed by its script shows up as Pi-hole. Secrets are removed before anything is stored. Environment variables keep their names only, and passwords, tokens and keys in command lines are redacted.

The pages

Dashboard
Totals, your Proxmox nodes with their guests, what needs attention (failed or never-scanned targets), and machines seen on the network that aren't documented yet.
Topology
Proxmox: one box per node, containing the node, its bridges and its VMs/LXCs, each wired to the bridge its NIC uses. Pulses show running guests. Network: gateway, switches, APs and clients. VLANs: members per network. Click for details, right-click for actions, double-click to open.
Services
Every systemd unit and container on every machine in one table. Filter by machine, state, type or text, and Export CSV exports exactly what you see.
Apps
Recognised apps by category, with the machines they run on and a link to their web UI.
IP addresses
One row per device, with all its addresses, MACs and networks. Link-local and Docker-bridge addresses are hidden until you ask for them.
Changes
Typed events: port opened, image updated, guest migrated, new device on a VLAN, and so on.
Unknown
Devices on the network that you haven't added. Infrastructure is listed first; phones and IoT are behind "show everything".

Updating

sudo atlas update

This pulls the new code (git pull --ff-only), writes a backup to /opt/atlas/backups (the last five are kept), pulls the new image and restarts. Your targets, stored passwords and keys, accounts, notes and history are kept. Database changes are applied automatically. The first time, if the shortcut doesn't exist yet, run git pull && sudo ./deploy/atlas.sh update in your clone.

Troubleshooting

A machine stays "not scanned yet"
Press Scan on its row. Scans are queued, so pressing it on several machines scans them all, one after the other.
A machine is "failed"
Open the line under its status for the reason. authentication refused: the username or password is wrong, or the machine refuses password logins (PasswordAuthentication no). host key: fetch and confirm it again. timeout: atlas can't reach port 22.
Partial scans
No sudo: Docker, port owners and root crontabs are missing. Tick use for sudo.
No Proxmox nodes or VMs
Add a node as proxmox-node with sudo, or fix the API token's permission (step 3).
A VM shows "state unknown"
atlas saw it in another node's configuration. Add the node it runs on, or the API.
A Pi-hole shows no services
It isn't a target yet. Add it as a machine (type pi or linux) and scan.

Security

  • Read-only by construction:
    • HTTP is GET-only and checked against an allowlist;
    • SSH runs a fixed set of read-only probe sections;
    • every call is written to a hash-chained audit log.
  • Credentials are encrypted at rest (AES-256-GCM) and never shown again. Back up /opt/atlas/secrets/atlas_master_key.
  • Keep atlas on your LAN or VPN. Don't expose it to the internet.

Details are in SECURITY.md in the repository.
